# Viral to Value

## 학교 네트워크 소셜 앱의 데이터 기반 제품 재건축

**코드잇 데이터 분석 15기 7팀**

학교 네트워크 기반 익명 소셜 서비스의 가입, 친구 연결, 질문 참여, 반응, 재방문을 분석하고, 그 결과를 **Ping 리빌드 UI/UX 프로토타입**으로 구체화한 프로젝트입니다.

> 빠르게 모인 사용자가 관계를 맺고, 받은 마음에 반응하며, 다시 방문하도록 하려면 무엇을 바꿔야 할까?

질문 완주율뿐 아니라 **가입 이후의 이용 경험 전체**를 분석합니다. 학교 활성화부터 후기 이용까지 일곱 가지 관점에서 문제를 진단하고, 첫 참여·질문 경험·반응과 대화·재방문의 네 구간을 재설계했습니다.

이 서비스는 질문에 어울리는 학교 친구를 선택하면 상대에게 익명의 지목인 **Ping**이 도착하고, 수신자가 결과를 확인하거나 답장하는 구조입니다. 기존에는 같은 학교의 가입자가 40명에 도달해야 질문 참여가 가능했으며, 힌트·답장·채팅 등에 하트를 사용했습니다.

## 2. 분석 구성

발표는 **유입과 교내 연결에 대한 사전 진단(Viral)**, **일곱 파트 분석과 종합 진단**, **제품 재구축**, **검증 계획**의 순서로 구성했습니다.

### 사전 진단: 빠른 성장을 어떻게 해석할 것인가

가입 시점과 학교별 친구 요청을 비교하되, 외부 미가입자의 유입과 기존 가입자 사이의 연결을 구분했습니다.

- **Social Connection Rate**: 학교 안에서 친구 요청이 최종 수락 관계로 이어진 정도를 살펴보는 지표입니다. 학교별 1인당 발송 수와 수락률을 결합해 비교하며, 외부 유입의 바이럴 계수로 해석하지 않습니다.
- **Time to Social Connection**: 최종 수락 요청의 생성부터 마지막 갱신까지의 간격을 수락 소요시간의 대용치로 사용합니다. 실제 최초 수락 시각을 직접 측정한 값은 아닙니다.

### 일곱 파트 분석

| 파트 | 핵심 질문 | 주요 분석 |
| --- | --- | --- |
| **Growth** | 가입한 학교는 실제로 활성화됐는가? | 40명 도달·미도달, 도달 전후 가입 추이, 학교별 확산 유형 |
| **Network** | 가입은 친구 관계와 이후 행동으로 이어졌는가? | 최종 수락 관계망, 고립·연결 집중도, 요청량·수락 상태·요청 지속 |
| **Content** | 사용자는 계속 새로운 질문을 만났는가? | 문구별 공급 집중, 신규 문구, 의미 반복, 학교별 공통·고유 질문 |
| **Interaction** | 질문을 끝낸 뒤에도 행동이 이어졌는가? | 시작·완료 전환, 완료 직후 첫 행동, 후속 행동과 재방문 |
| **Value** | 받은 반응은 다시 참여할 이유와 연결됐는가? | 행동 군집, 지목의 발신·수신 구조, 답장·힌트·결제, 반응과 다음 날 투표 |
| **Trust** | 불편한 질문을 어떻게 구분하고 검토할 것인가? | 질문 주제와 신고 사유, 질문당·노출 대비 신고, 게시 전 검토 모델 |
| **Continuation** | 초기 열기가 지난 뒤에도 핵심 이용이 이어졌는가? | 가입 코호트의 후기 행동 관측, 출석 중심 이용, 활동 공백과 재방문 |

Viral은 전체 문제를 설정하는 사전 진단입니다. 본문의 일곱 분석 파트는 Growth부터 Continuation까지이며, 저장소의 분석 폴더 수와 발표의 일곱 파트는 구분합니다.

| Continuation | 후기 관측자 중 **83.91%가 출석만 기록** | 2023년 5월 가입 코호트 중 D181~270에 관측된 사용자 기준 |

종합하면, 초기 가입과 연결 규모뿐 아니라 **첫 참여 이후 어떤 질문을 만나고, 반응을 주고받으며, 다음 방문으로 이어지는지**를 함께 다룰 필요가 있었습니다.

## 4. 분석에서 제품 재구축으로

분석에서 확인한 문제를 네 가지 이용 구간에 연결했습니다. 아래 내용은 **실제 운영에 적용하기 전의 설계 제안**입니다.

### 01. 첫 참여

40명에 도달하지 못한 학교도 있었지만, 기존 이용 구조에서는 개방 전까지 초대하며 기다려야 했습니다. 학교 인원에 따라 참여 범위를 단계적으로 여는 흐름을 설계했습니다.

| 학교 인원 | 제안한 이용 범위 |
| --- | --- |
| 0~14명 | 서비스 소개와 친구 초대 |
| 15~24명 | 실제 질문 2개 참여, 학교·전체 범위 질문 제안 |
| 25~39명 | 학교 로컬 질문, 받은 Ping 결과 읽기 추가 |
| 40명 이상 | 일반 10문항과 반응·답장·역질문·채팅 등 전체 기능 |

15명과 25명은 분석으로 입증한 최적 기준이 아닌 **운영 가설**입니다. 친구 연결 조건은 학교 개방 기준과 별도로 확인하며, 적용 후 참여율과 안전 지표를 보고 기준을 조정해야 합니다.

### 02. 질문 경험

질문의 종류가 존재하는 것과 이용자가 새로운 질문을 만나는 것은 달랐습니다. 분석한 10개 학교에서 질문조각의 **96.08%는 10개 학교에 공통으로 등장한 문구**였고, 한 학교에서만 등장한 고유 문구는 1개였습니다. 신규 문구 공급과 의미 반복 문제도 함께 확인했습니다.

- **학교 로컬 질문**: 축제·행사 등 함께 겪는 학교생활을 일반 10문항에 반영합니다.
- **사용자 질문 제안**: 학교생활을 직접 경험하는 이용자가 학교·전체 범위의 질문 소재를 제안하는 경로를 둡니다. 신규 공급을 보완하기 위한 설계이며, 공급 증가 효과는 별도 검증이 필요합니다.
- **검토와 노출 관리**: 규칙·모델·담당자 검토를 연결하고, 게시 이후에도 의미 중복·개인별 재노출·신고를 살펴봅니다.
- **건너뛰기 이유**: 후보 부족, 반복, 불편함을 구분해 후보 구성과 질문 추천·검토에 반영하는 흐름을 제시합니다.

### 03. 반응과 대화

질문 완료 이후의 행동이 여러 화면으로 흩어졌고, 지목을 많이 받은 집단이 반드시 많이 답장하지는 않았습니다. 완료 이후 실제 반응을 확인하고 돌려줄 수 있는 경로를 설계했습니다.

- 완료 화면에서 실제 도착한 결과·반응 확인으로 연결
- 기본 이모지·스티커·50자 이내 짧은 답장의 무료화
- 보낸 Ping의 전송·열람·반응 도착 상태 구분
- 상대의 신원을 알아내지 않고 질문으로 답하는 역질문
- 무료 반응 이후 원하는 이용자만 선택하는 채팅

채팅은 200하트 사용 후 첫 요청으로부터 72시간 동안 실제 답장이 없으면 개설 하트를 반환하는 조건을 제시했습니다. 비용과 기간은 시안의 가정이며, 실제 상품·운영 정책으로 확정한 값은 아닙니다.

### 04. 재방문

후기 방문이 출석에 치우친 관측을 바탕으로, 다시 들어온 순간의 상태와 다음 행동을 연결했습니다.

- 새 Ping·새 질문·새 친구 등 현재 상태를 먼저 보여주는 홈
- 실제 새 정보가 있을 때만 보내는 알림
- 출석 보상 수령 후 받은 Ping이나 선택 미션으로 이어지는 경로
- 받은 결과 모아보기, 대표 배지 선택, 이용자가 직접 정하는 공개 범위

### 클러스터를 반영한 설계

Value 분석에서는 10개 학교의 **4,849명**을 대상으로 **GMM K=4** 군집을 해석했습니다. 군집별 별도 서비스를 만드는 대신, 같은 제품 흐름 안에 서로 다른 이용 특성을 반영했습니다.

| 군집 | 관측한 행동 특성 | 연결한 개선 화면 |
| --- | --- | --- |
| C0 적극 발송·확인형 | 발송과 확인·반응 행동이 활발 | 보낸 Ping 상태, 실제 반응 확인, 역질문 |
| C1 수신 우위 일반형 | 받은 지목에 비해 답장이 적음 | 무료 이모지·스티커·짧은 답장 |
| C2 유료 이용형 | 유료 이용 경험이 상대적으로 많음 | 역질문, 선택 채팅, 비용·무응답 반환 조건 |
| C3 고수신 저반응형 | 지목 수신은 많지만 반응은 적음 | 내 결과, 대표 배지, 선택 공개 |

군집은 행동을 해석하기 위한 분석 도구입니다. 특정 군집에만 기능을 허용하거나, 개인의 성격·의도를 단정하는 기준으로 사용하지 않습니다.

## 5. 기대효과와 검증 계획

**현재까지의 결과는 데이터 분석과 프로토타입 구현입니다.** 아래 지표는 개선 성과가 아니라, 실제 적용 시 확인할 검증 계획입니다.

학교 안에서 이용자끼리 영향을 주고받는 특성을 고려해 학교 단위 실험 또는 단계적 적용을 검토합니다.

| 개선 구간 | 확인할 핵심 지표 | 함께 확인할 부작용 |
| --- | --- | --- |
| 첫 참여 | 단계별 개방 후 첫 질문 참여율, 40명 도달 학교 비율과 도달 후 7일 내 첫 질문 참여율 | 건너뛰기, 노출 대비 신고 |
| 질문 경험 | 의미 반복률, 신규 질문 노출 비율 | 전체·안전 사유별 노출 1,000건당 신고 |
| 반응과 대화 | 24시간 내 반응 발생 비율, 다음 날 투표 참여율 | 알림 차단·해제 |
| 재방문 | 방문 후 핵심 행동 전환율 | 알림 차단·해제 |

참여가 증가하더라도 신고나 원치 않는 알림이 함께 늘어나는지 확인해야 합니다.

## 6. 데이터 범위와 해석상의 한계

### 데이터 범위

- **서비스 DB와 분석용 마트**: 가입, 학교, 친구 요청, 질문, 지목, 열람·답장, 신고, 출석, 결제 등을 연결해 분석했습니다. 테이블과 지표별 관측 범위는 다릅니다.
- **Hackle 방문 로그**: 2023.07.18 ~ 2023.08.10. 질문 시작·완료와 완료 이후 행동 분석에 사용했습니다.
- **10개 학교 분석**: Content·Value 및 일부 Trust 분석에 사용했습니다. 전체 학교 분석과 표본을 구분합니다.
- **2023년 5월 가입 코호트**: 가입일 기준의 구간별 행동 관측과 후기 이용을 살펴봤습니다.

따라서 `2023.07.18 ~ 2023.08.10`을 프로젝트 전체 데이터 기간으로 사용하지 않습니다. 구체적인 필터·분모·기간은 각 분석 코드와 문서를 기준으로 확인합니다.

<details>
<summary><strong>분석 결과를 읽을 때의 해석 원칙</strong></summary>

7. **검증되지 않은 가설을 성과로 쓰지 않습니다.** C1·C3 답장 수준과 학교 활성 유지 일수의 관계에 대한 가설은 지지되지 않았으며, 리빌드의 운영 효과는 후속 실험이 필요합니다.

## 10. 팀 협업 규칙

### 브랜치 전략

`main`을 기준으로 작업별 브랜치를 생성합니다.

- `main`에 직접 커밋하거나 Push하지 않습니다.
- 작업 전 `main`의 최신 내용을 Pull합니다.
- 담당 작업별 브랜치를 생성하고, 하나의 브랜치에서는 하나의 분석·수정 목적을 다룹니다.
- 완료한 작업을 Push한 뒤 Pull Request를 생성합니다.
- 최소 1명의 팀원이 코드를 검토한 후 `main`에 병합합니다.
- 병합이 완료된 작업 브랜치는 삭제합니다.

### 작업 흐름

1. `main` 최신화
2. 작업 브랜치 생성
3. SQL·Python·문서 작업
4. Commit 및 Push
5. Pull Request 생성
6. 팀원 코드 리뷰
7. `main` 병합 및 작업 브랜치 정리

### 브랜치 타입

| 타입 | 용도 |
| --- | --- |
| `feat` | 새로운 기능·분석·데이터 마트 추가 |
| `fix` | 코드·데이터 처리 오류 수정 |
| `docs` | README·데이터 명세서·분석 문서 작성 및 수정 |

브랜치 이름은 `타입-작업명#이슈번호` 형식을 사용합니다.

```text
feat-question-attempt-mart#1
fix-event-deduplication#2
docs-project-readme#3
```

### 커밋 컨벤션

```text
[Feat] 질문 진행 시도 마트 생성
[Feat] 질문 순서별 스킵률 분석 추가
[Fix] 중복 완료 이벤트 집계 오류 수정
[Docs] 프로젝트 README 작성
```
